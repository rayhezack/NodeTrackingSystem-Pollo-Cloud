# AI design task execution and review

Task Monitor uses the application's white surfaces and primary blue. Its seven segments represent observed server phases; individual event batches are visible in the task list. Completed phases are pale blue, the current phase is blue, future phases are gray, and paused/failed states have text and semantic color. Hover, keyboard focus and click open task details. Completion preserves the light theme and opens the existing draft review on demand.

## Background execution

The Pollo Cloud client creates a persisted job and receives its ID immediately. The application task service owns the execution connection, outside route component lifecycles. Navigating between app pages or requirements unsubscribes the view from polling; it does not abort execution or send a cancellation request. Returning to the requirement replays persisted progress for the same owner/job.

`ai_tracking_jobs` in the existing D1 database owns state and leases. A partial unique index allows only one queued/running/paused job per owner and requirement. Atomic claims and conditional state writes prevent double execution and prevent a late response from overwriting paused/cancelled work. Another Worker isolate observes stop/pause within five seconds; an in-flight provider request may already have been accepted and cannot be unbilled. No generated draft is applied to Base automatically.

Pause retains completed model checkpoints. Resume reuses those checkpoints and reruns the interrupted call. Cancel is terminal; a new generation creates a new job. Checkpoint keys include the model, embedded Skill and exact prompt, preventing reuse after a policy or context change. Status and cancellation endpoints require the same authenticated owner as the job.

A browser connection alone cannot provide durable execution on Workers. The independent `/api/cron/ai-jobs` dispatcher is therefore declared at the platform's minimum five-minute interval. It accepts only the platform-injected cron trigger header. If the browser closes, the connection fails or an invocation dies, the expired lease is recovered on the next dispatch; recovery can take up to five minutes, plus queue wait. It processes one job per dispatch and yields before the platform's four-minute cron ceiling. Completed model checkpoints are retained. This is recovery rather than a promise of uninterrupted execution through platform failures. Pollo Cloud does not expose a queue/workflow binding in the current app configuration.

Deployment must include the new Worker routes and cron declaration. After deployment, inspect `pollocloud cron list --name app-tracking-management` and run the dispatcher once with the CLI to confirm platform scheduling. No external notification or access expansion is introduced. Local Nest development retains the existing generation API; the persisted controls are enabled on the D1-backed Pollo Cloud runtime.

## Review layout

The Astryx review area follows the existing inbox/detail pattern: event search and independent selection in the navigation pane, one event's content in the reading pane. Event specifications, parameter rows, questions/evidence and governance checks occupy separate tabs. Parameter search and the questions filter operate only on the active event. Secondary fields (condition, platform, default, request notes and questions) remain accessible in parameter details. Confirmation and combined event/parameter counts remain in the existing dialog footer. Each parameter can be selected independently; the table header applies bulk selection only to filtered rows, and event-wide select/clear controls preserve choices when switching events. Explicit empty lists import the event only. Both runtimes validate event and parameter identities against the stored draft and apply the same allowlist before validation and after governance inheritance, so an unchecked official parameter is never silently restored. This controls the request copy only; official library contracts remain unchanged. Older clients that omit parameter choices retain the existing import-all behavior.

The Astryx theme binds to existing product tokens and is compiled during the Pollo Cloud build. Kubai uses the unmodified upstream engine, with product-specific lifecycle and theme adapters. Icon assets are checked at 24/28 px, rest/hover/intermediate states and multiple palettes. Component previews in `logs/` contain explicitly marked demonstration data and are not shipped as application routes.
