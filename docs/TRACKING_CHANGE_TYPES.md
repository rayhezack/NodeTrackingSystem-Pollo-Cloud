# 埋点变更类型与归档

事件只保留四种类型。类型描述对正式库的影响，与需求单的流程阶段分开判断。

| 类型 | 判断标准 | 归档行为 |
| --- | --- | --- |
| 新增 | 正式库中不存在该事件 | 创建正式事件和已确认参数 |
| 修改 | 已有事件补可选参数或扩展枚举等兼容增量 | 应用已评审增量，保留其他正式字段和参数 |
| 废弃 | 已有事件停止使用 | 先保存废弃事件和参数历史，再从有效正式库移除 |
| 仅校验 | 正式定义不变，仅验证上报或修代码使其符合现有规范 | 关闭需求流程并保存验收信息；不读写正式事件、参数、枚举和废弃库 |

「口径调整」不再单列。读取历史记录时展示为「修改」，新的显式保存使用规范值；不批量重写历史记录。旧客户端提交的「口径调整」也按「修改」处理。「仅开发校验」「开发校验」「不修改正式库」「仅校验不归档」统一映射到「仅校验」。历史「不变」仍按原有「修改」解释，避免无依据改变旧任务的发布行为。

原样复用归「仅校验」，复用并补参或扩枚举归「修改」。AI 类型由服务端检查正式快照后根据实际增量计算；用户只选部分参数时，应用前再次按所选参数计算。需求专属说明、页面位置和验收备注不改变正式定义。参数层保留「新增、修改、废弃」三项，「仅校验」是事件级发布策略。

核心业务含义、触发边界或统计单位变化，应设计新的事件 ID；不能借「修改」重释同一事件的历史数据。现有正式事件元数据、参数类型、必传规则等仍受正式契约保护，普通需求归档不直接覆盖。

未选入需求单的正式参数不会因此废弃或删除；正式事件的「修改」也不能用当前需求的参数子集替换完整正式参数库。同需求内各事件单独判断变更类型，统一完成流程时只有需要变更的事件参与正式库同步。
