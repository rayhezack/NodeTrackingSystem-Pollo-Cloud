# D1 主存储与 Base 同步

App 经 Worker 鉴权和现有业务规则访问 D1。Base 是异步查询副本。API 不等待 Base 写入或流程通知；业务记录与 outbox 在同一个 SQLite batch 事务中提交。新记录使用稳定 d1_UUID，Base ID 映射独立保存，App 链接不会因异步创建改变。

## 切换

先导出 D1 备份，再从数据同步页开始导入。导入期间应用业务写入冻结，原 Base 写入闸门由迁移占用，既有在途写入结束后才能开始。逐页导入 Web/App 全部 16 张表，保留 Base 原记录 ID、关联和原字段；每页可重入。全部完成后同一事务切换 mode=d1 并释放迁移闸门。不允许已启用 D1 后重新从 Base 覆盖主库。迁移期间应停止直接编辑 Base；App 无法阻止有 Base 编辑权限的人绕过应用操作。

现有 Base 访问凭证继续由服务端管理，个人 SUN CLI 凭证不复制到 App。独立权限检查、正式契约、仅校验/修改/新增/废弃行为沿用原逻辑。仅校验依然不会同步正式库。

## 提交与冲突

请求中的 Bitable 操作被映射到 D1 unit of work：读到自己的暂存写入，失败请求不提交业务记录。提交校验所读表的 revision，避免并发覆盖和重复判定中的幻读。当前为保守的表级乐观并发检查，冲突会整体回滚并提示重新保存；不再让普通编辑等待全局 Base 写锁。单条业务记录上限 60 KB，大附件继续使用已有文件存储。

## 同步与恢复

浏览器在成功写入后尽力启动独立 dispatch；关闭页面不取消已持久化待办，五分钟 cron 兜底。消费端独立加锁，按 outbox 顺序处理，已完成记录不会重放。普通更新只同步此次字段 patch，不把 Base 系统字段和其他历史字段整行覆盖。关联 d1_ID 在提交 Base 前转换为映射 ID。

失败的确定性更新在后续 dispatch 重试，最多五次，也可在页面手动重试。新增请求发出后结果不明确，或消费者在执行中被杀死，任务保留 processing，停止后续消费；不能自动再创建。需管理员核对 Base 的实际记录并恢复映射和任务状态。这个限制优先防止重复记录，不宣称外部 HTTP exactly-once。通知也经 outbox，通知发送不作为 D1 保存成功的条件。

Base 直接编辑不回流 D1。不要将 Base 变更与 D1 自动互相覆盖。回滚主存储前必须先核对尚未同步的 D1 数据，禁止简单切回旧 Base 丢弃未同步变更。

## 性能验收

高频详情按需求 ID 查询，参数按归属/evt_id 筛选，不再通过远程 Base 拉全表。保存后使用 API 返回数据更新现有参数列表。响应包含 X-Tracking-Storage 与 Server-Timing，用户侧应测从点击到可操作/保存成功。目标为正常网络下 P95≤3 秒；没有足够真实样本前不声称达标。图片预览、PRD、通讯录搜索仍是外部服务，不属于 D1 业务行存储。
